# Architecture: Ecosystem Terrarium (Complex Mode)

Working title. Roblox game, Luau. This document describes how the code is organized and why. Game rules live in `docs/design.md` (exported from the design doc). When the two disagree, the design doc wins for gameplay and this file wins for code structure.

Status labels: **[Locked]** decided in the design, **[Default]** sensible default, change if a better one is found, **[TBD]** must be measured or decided during prototyping.

## 1. Goals and constraints

1. **Server-authoritative deterministic simulation.** The same seed, setup, and command log must always produce the same run. Leaderboard fairness, weekly seeds, replay, and anti-cheat all depend on this. **[Locked]**
2. **Speed must not change the result.** The simulation advances in fixed steps of 1 in-game hour. Speed (1x, 10x, 50x) only changes how many steps run per real second. **[Locked]**
3. **Many sessions per server.** Every player has a plot, and every plot may run a simulation with hundreds of animals. Cost per step is the main technical risk.
4. **Data-driven species.** Adding a species means adding a data entry, never new logic. **[Locked]**
5. **Visuals are separate from logic.** Server simulates data. Clients render and interpolate. No Humanoids for animals. **[Default]**

## 2. Layers

```
shared/sim   pure Luau simulation core, no Roblox services, runs headless
shared/data  species, biomes, starter packs, disasters (plain tables)
server       sessions, scheduling, economy, leaderboards, persistence, trading
client       rendering, UI, input, charts
```

Dependency rule: `client` and `server` may require `shared`. `shared/sim` may only require `shared/data`, `shared/types`, and `shared/util`. `client` never requires `server`, and the two never require each other.

`shared/sim` must not use `game`, `workspace`, `task`, `os.time`, `os.clock`, `math.random`, or any Roblox API. This keeps it deterministic and lets it run under Lune for tests and balance tuning.

### 3.1 Toolchain and workflow

Two tools, two jobs:

- **Rojo** syncs files into Studio. Files in `src/` are the source of truth for every script. Version control, formatting, linting, and headless tests all depend on this.
- **Roblox Studio MCP (built into Studio)** lets the agent act inside the open Studio session: playtest, read console output, take screenshots, simulate input, inspect instances, insert assets, and run Luau. It is not used to edit Rojo-managed scripts.

```
agent edits src/*.luau ──▶ Rojo (rojo serve) ──▶ Studio
agent ──▶ Studio MCP ──▶ playtest, console, screenshot, inspect, build models/UI
agent ──▶ Lune ──▶ headless sim tests, data validation, balance harness
```

Rojo project sketch (`default.project.json`). Workspace is intentionally not mapped, so models, terrain, and decorations built in Studio are untouched by sync. **[Default]**

```json
{
  "name": "EcosystemTerrarium",
  "tree": {
    "$className": "DataModel",
    "ReplicatedStorage": {
      "$className": "ReplicatedStorage",
      "Shared": { "$path": "src/shared" }
    },
    "ServerScriptService": {
      "$className": "ServerScriptService",
      "Server": { "$path": "src/server" }
    },
    "StarterPlayer": {
      "$className": "StarterPlayer",
      "StarterPlayerScripts": {
        "$className": "StarterPlayerScripts",

      }
    }

```

What lives where:

| Content | Home |
|---|---|
| Scripts, data tables, types | Files in `src/` |
| Animal visuals | Cubes generated by code for now. Real models later, in the Studio place (built through MCP or by hand) |
| UI templates, plot terrain, decorations | The Studio place (built through MCP or by hand) |
| Species and balance data | Files in `src/shared/data/` |

Models and UI that live only in the place must be saved from Studio. Anything the code needs to look up at runtime (for example an animal model per species) is found by a name convention defined in the species data, never by hardcoded paths in the sim. **[Default]**

MCP is for verification and building, not for correctness. A playtest through MCP never replaces a Lune test.

## 4. Simulation core (`shared/sim`)

### 4.1 World state

A `World` holds everything needed to continue a run:

- `step` (integer, in-game hours since start), `seed`, RNG state
- `zones` (up to 4): terrain grid, water, light, nutrient pool, plant biomass, capacity
- `transitions`: procedurally generated links between zones
- `entities`: animals and fungi as struct-of-arrays (position, zone, species index, age, hunger, health, state, target) for cache-friendly iteration
- `speciesState`: per-species counters (population, births, deaths by cause, first seen step)
- `flags`: collapse timer, active disasters, active sabotage effects
- `eventLog`: append-only record used by the final report

Entities are referenced by integer id. Iteration is always in ascending id order. Never iterate Lua tables with `pairs` where order affects results.

### 4.2 Step pipeline

One call to `Sim.step(world, commands)` advances exactly 1 in-game hour. Order is fixed:

1. Apply commands scheduled for this step (disasters, sabotage, nothing else from outside).
2. Environment: season, weather, water, light, nutrient flow.
3. Plants: growth and regrowth, capacity limits, seed bank floor.
4. Aging and metabolism: hunger, health, natural death.
5. Perception and decision: per-entity state machine (`idle`, `forage`, `hunt`, `flee`, `mate`, `migrate`, `rest`).
6. Movement.
7. Interactions: feeding, predation resolution (size rule), competition, disease spread.
8. Reproduction and speciation rolls.
9. Deaths: record cause, produce carcass, decomposition returns nutrients (fungi required).
10. Zone migration through transitions.
11. Collapse detection and grace period.
12. Economy accrual and achievement counters.
13. Append events and decide whether a snapshot is due.

Each system gets its own RNG stream derived from `(seed, systemId, step)`. This keeps results stable when one system is changed or skipped.

### 4.3 Species data schema

Species are plain tables validated by `tools/validate_data`. Sketch (adjust field names when implementing):

```lua
export type Species = {
    id: string,                    -- "Panthera leo"
    commonName: { id: string, en: string },
    taxonomy: { kingdom: string, phylum: string, class: string, order: string,
                family: string, genus: string },
    iucn: "LC" | "NT" | "VU" | "EN" | "CR" | "DD",
    estimated: { [string]: boolean }?,      -- fields that are estimates
    role: "plant" | "herbivore" | "carnivore" | "omnivore" | "scavenger" | "decomposer",
    diet: { { target: string, efficiency: number } },   -- explicit species or genus ids
    size: number,
    sizeRatioMax: number,          -- how large a prey, relative to self, can be killed
    habitat: { biomes: { string }, water: "none" | "semi" | "full", climate: ClimateRange },
    regions: { string },           -- continent or ecoregion codes
    lifespanDays: number,
    hungerRate: number,
    reproduction: { rate: number, gestationDays: number, litter: number },
    speed: number,
    diseaseSusceptibility: number,
    speciation: { weight: number, candidates: { string }? },
}
```

Rules enforced by the validator: every diet target exists, every family has at least one species, estimated fields are flagged, taxonomy is complete.

### 4.4 Rules that must be encoded in data or systems

- Plants cannot go extinct. A seed bank keeps a floor; "near extinction" means below 10% of zone capacity. **[Locked]**
- Predator can only kill prey within `sizeRatioMax`, with exceptions marked in data (pack hunting, venom). **[Locked]**
- Apex predators reproduce very slowly. **[Locked]**
- Competition acts on niche overlap and shows up as starvation and failed breeding, not direct kills. **[Locked]**
- Fungi extinction slowly lowers plant capacity. **[Locked]**
- Bacteria and archaea are not simulated. **[Locked]**
- Invasive species effects (naive prey, enemy release, new disease) depend on whether a species' `regions` overlap the terrarium region. **[Default]**

### 4.5 Collapse and end conditions

Evaluated in step 11. **[Default]**

- Animal collapse: remaining animals belong to one feeding guild, or total animal species is 2 or fewer.
- Plant collapse: plant biomass below 10% of capacity.
- Grace period: 1 season (90 in-game days). Condition clears, timer resets.
- A zone that loses nearly all inhabitants becomes a dead zone but the run continues until the global condition holds.
- Score time is recorded at collapse start, not at stop.
- Hard caps: 24 real hours, and for ranked runs 100 in-game years. Manual stop is always allowed.

### 4.6 Speciation

New species appear only from families or ordos already present, must fit biome and region, and must be rare enough to feel special. Rolls use the speciation RNG stream. A species enters the player's index only after surviving a rarity-dependent number of seasons (LC 1, NT 2, VU 4, EN 8, CR 12). **[Default]**

## 5. Time, speed, and scheduling

| Speed | In-game per real second | Purpose | Leaderboard |
|---|---|---|---|
| 1x | 1 hour | Observation and learning | No |
| 10x | 10 hours | Simulation | Yes |
| 50x | 50 hours | Simulation | Yes |

**[Locked]** 1x = 1 step per real second. Ranked runs allow only 10x and 50x. **[Default]** Switching speed mid-run is allowed.

The `SessionService` owns a scheduler loop on `RunService.Heartbeat`:

1. Each active session accrues `dt * speed` steps of debt (fractional carry kept).
2. Sessions are served round-robin, each limited by a per-frame time budget (**[TBD]**, start at 2 ms per session and a global budget of about 8 ms).
3. If a session cannot keep up, it runs slower in real time. Results never change because steps are fixed. Ranked scoring uses in-game time, so lag does not hurt fairness.

Required invariant, covered by a test: running N steps in one batch, in batches of 1, or in any mix must produce the identical world hash.

## 6. Server design

### 6.1 Services

- `PlotService`: assigns plots, owns the terrarium layout and upgrades, loads and unloads plot visuals.
- `SessionService`: creates runs from a validated setup, owns the scheduler, handles speed changes and manual stop.
- `SetupService`: validates starter pack, terrain, family placement, the 10-per-species limit, slot limits, disaster choices, ranked entry fee.
- `FounderService`: resolves a family to founder species using the seed, plus paid survey and genus narrowing.
- `EconomyService`: income accrual from the sim's economy counters, spending, fees, prices.
- `LeaderboardService`: submits run results to the right boards (see 6.3).
- `IndexService`: tracks family ownership, discovered species, survival thresholds, set bonuses.
- `TradeService`: seeds (bibit) crafting, cooldowns, same-tier checks, daily limits.
- `SabotageService`: opt-in list, pricing by saboteur wealth, one per saboteur per run, protection window, victim compensation. Turns an accepted action into a command with a target step.
- `ExhibitService`: exhibit slots, offline income (cap 8 hours, based on rarity), ratings (one per player per day, minimum progress).
- `QuizService`, `AchievementService`, `EventService` (daily and weekly).

### 6.2 Commands and replay

External input into a running sim is only a **command** stamped with the step where it takes effect. Setup, seed, and the full command log are stored with the run. A ranked run can be replayed headless to verify its result. Sabotage and disasters are commands, so runs with sabotage remain deterministic and replayable. **[Default]**

### 6.3 Leaderboards **[Locked rules, Default implementation]**

Separate boards: per biome and terrarium tier, ranked run, weekly seed, sabotaged runs, and metrics (duration, peak diversity, money). One best run counts. 10x and 50x share boards. 1x runs are never submitted. Weekly seed boards hand every player the same seed and starter pack.

### 6.4 Persistence (later phase)

Player profile: money, owned families, index entries (species, first seen, thresholds met), upgrades, decorations, exhibit contents, achievements, quiz history, trade cooldowns, last-seen time for offline income. Leaderboards use ordered stores. Schema versioning from day one. Exact storage approach is decided when Phase 1 starts. **[TBD]**

## 7. Client design

- `RenderController` receives snapshots and events and drives the 3D scene. Animals are lightweight objects moved with CFrame or tweens, with no Humanoid.
- **Placeholder visuals for now:** every entity is a plain cube Part generated by code, sized from the species `size` through one scale function in a client config module, and colored by role with a small per-species shade variation. Cube creation sits behind a single factory (`EntityView.create(speciesId)`) so real models can replace cubes later without changing the renderer or the sim. **[Default]**
- **Level of detail by speed:** at 1x full animation (hunts, mating, death). At 10x simplified poses and fewer effects. At 50x minimal markers and mostly charts. **[Default]**
- Hard cap on rendered entities per plot (start 150, **[TBD]**). When the sim has more individuals than the cap, render nearest to the camera and aggregate the rest.
- `UIController`: speed control, graphs (population per species, per guild, plant capacity, money), setup screens, index tree with taxonomy, report viewer, shop.
- Charts consume `Stats` messages, not raw entity data.

## 8. Replication protocol

All remotes are validated on the server. The client never sends gameplay results.

Server to client:
- `RunStarted(runId, seed, setupSummary)`
- `Snapshot(step, deltas)` entity id, quantized position, zone, state; sent every N steps depending on speed and distance
- `Events(step, list)` births, deaths with cause, hunts, migrations, speciation, disasters (for animations and notifications)
- `Stats(step, series)` sampled per day or season for charts
- `RunEnded(report)`

Client to server: `StartRun(setup)`, `SetSpeed(10 | 50 | 1)`, `StopRun`, plus economy, trade, and sabotage requests. Each request is rate-limited and checked against server state.

## 9. Final report

The event log is aggregated after the run into the report:

- Summary: duration, money, diversity, peak species count.
- Population timelines per species.
- Cause-of-death breakdown per species.
- Causal chain for the collapse, derived by tracing the largest population declines backward through feeding relations ("zebra fell after drought, lions starved, ...").
- Notable events: speciation, invasions, disasters, migrations, local extinctions.
- Per-year replay of snapshots at low cost, so fast runs remain educational. **[Default]**

## 10. Economy hooks

The sim exposes counters per step (effective population per species, diversity index inputs, native ratio, active disaster level). `EconomyService` converts them to money using the formula from the design doc. Constants live in `shared/data/economy.luau` so they can be tuned without touching logic.

## 11. Testing

Run with Lune, no Studio needed.

- **Golden seed tests:** fixed setup and seed produce a known world hash after N steps.
- **Speed invariance:** batching steps differently yields the same hash.
- **Invariants:** populations never negative, plants never reach zero, no entity in two zones, diet targets resolve.
- **Data validation:** schema, taxonomy completeness, valid IUCN codes, diet graph reachable, every producer has a consumer.
- **Balance harness (`tools/balance`):** runs hundreds of seeds of a starter pack and reports distribution of time to collapse, species counts, income. Used before changing any constant.
- **Performance benchmark:** steps per second for 100, 300, 600 entities, tracked over time. Run once in Lune (pure cost) and once in Studio through MCP `execute_luau` or a playtest (real engine cost).
- **Studio integration checks (via MCP):** playtest starts without console errors, a run can start, speed can change, snapshots reach the client, the report appears. Use `get_console_output` and `screen_capture` as evidence.

## 12. Roadmap

1. **Phase 0 (prototype):** first set up the toolchain (Rojo, Rokit, Lune, Studio MCP in opencode) and settle module loading across Roblox and Lune. Then one biome (savanna), one starter pack, 15 to 20 species (plants, herbivores, carnivores, scavenger, decomposer). Sim core, fixed steps, collapse, simple report, 1x/10x/50x. Question to answer: is balancing the ecosystem fun?
2. **Phase 1:** money, upgrades, index with taxonomy tree, persistence.
3. **Phase 2:** speciation, disasters, invasive species, ranked boards and weekly seed.
4. **Phase 3:** multi-zone, migration, water zone, exhibit, trade, sabotage.
5. **Phase 4:** events, achievements, quizzes, special era biome.

## 13. Open technical questions

- Entity cap per plot and per server, and the right step time budget. Measure in Phase 0.
- Spatial structure: uniform grid per zone is the default. Revisit if hunts across large zones are slow.
- How to represent aquatic movement in 2D grid versus 3D. Default: 2D grid with depth layer flag.
- Whether very large populations (insects) are simulated as individuals or as aggregate counts inside the same pipeline.
- Co-op mode: how zones and commands are shared between players.
- **Module loading across Roblox and Lune.** Roblox code normally requires modules through instances (`script.Parent.X`), which Lune does not have. Phase 0 starts by picking one convention that works in both (string-based requires if the current Roblox and Lune versions both support them, otherwise a thin loader shim used only by tests). Verify before writing the sim.
- Tool versions are pinned in `rokit.toml`. Pick them when the repo is created.
